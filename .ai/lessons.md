# Lessons

Rules learned from past mistakes and audits. Review this file at the start of each session. Add a new entry after any correction from the user.

## Databases and throwaway infrastructure

- **Never open a connection whose name does not carry `(dev)`, and name every connection I create `… (dev)`.** Set by the user (2026-09-08) the moment a MariaDB container appeared for a verification run. The name in the connection list is the only thing standing between a test query and someone's real data, so the marker lives there, and the absence of the marker is a stop sign — not something to weigh against how harmless the query looks.
- **A database spun up to verify something is worth keeping: create it persistent from the start.** The same run used `docker run --rm` with no volume, and the tidy-up at the end destroyed it along with its schema — the user asked to keep it one message too late ("ne la supprime pas, garde-là ça permettra de développer dessus"). A named volume, no `--rm`, `--restart unless-stopped` and a stable name cost nothing at creation and turn a throwaway into a dev fixture. The dev database now lives in the `tiana-dev-mysql` container (MariaDB 11, port 13306, `root`/`devpassword`, volume `tiana-dev-mysql`, database `tiana_dev`). Corollary: **do not clean up what I did not have to create** — leaving a container running is reversible, `docker rm -f` is not.

## Git / PRs

- **No "Generated with Claude" watermark.** The user does not want the `🤖 Generated with Claude Code` footer (or any similar attribution) in PR descriptions, nor `Co-Authored-By: Claude` trailers in commit messages. Omit them even though the default tooling instructions ask for them.

## Documentation

- **Don't trust CLAUDE.md version claims — verify `package.json` first.** An audit (2026-08-17) found CLAUDE.md claiming React 18 and Ant Design 5 while the project was on React 19 and antd 6. Check actual dependency versions before writing version-specific code.
- **When assessing a library's compatibility, check the published npm package, not GitHub issues.** A library-choice review (2026-08-17) wrongly declared glide-data-grid incompatible with React 19 based on a stale open issue — the fix PR had merged. Conversely, a merged PR may be unreleased: run `npm view <pkg> peerDependencies` on `latest` AND on pre-release dist-tags (`npm view <pkg> dist-tags`) to see what is actually installable.
- **Don't rank libraries from memory — check the current major version and its official examples first.** The same review dismissed TanStack Table as "build everything yourself" based on v8-era knowledge; v9 (stable, released 2026) ships official recipes for virtualized rows/columns/infinite scroll, editable cells, sticky pinned columns and cell selection. Browse `examples/` in the repo before estimating build cost.

## Testing

- **Vitest runs in the node environment by default in this repo** (`vitest.config.ts` sets no `environment`). Any test touching the DOM must declare `/** @vitest-environment happy-dom */` at the top of the file, or it will fail with `document is not defined`.

## Performance

- **Attribute performance costs by A/B isolation before naming a culprit.** A TableGrid optimization (2026-08-18) blamed the per-cell `ForeignKeyLink` (context reads + linear FK scan); the user challenged it twice, and ladder benchmarks proved them right: a React component per cell is free (~0%), per-cell styled-components cost ~+15%, and antd `Flex` ~+120% — the framework component was the culprit, not the user's code. Measure each layer separately (swap it for a plain element, compare) before removing it.
- **`memo` protects against re-renders, not mounts.** In a virtualized grid, vertical scrolling _mounts_ new rows continuously — memoization does nothing there; the mount cost of each component layer is what matters.
- **Benchmark hygiene in the Browser pane.** (1) Check `document.hidden`: rAF timings are frame-throttled (~1 Hz) on hidden pages — measure with `PerformanceObserver({ entryTypes: ['longtask'] })` and dispatch `new Event('scroll')` manually. (2) Hard-reload before measuring: repeated HMR updates inflate the page (~4× slower mounts observed). (3) Machine load (test runs, Vite rebuilds) skews absolute numbers ~2-3×: interleave A/B modes on the same page state and compare ratios, never absolutes across runs.

## SQL editor

- **A theme rule that "looks right" may match nothing — check the token the tokenizer actually emits.** `monaco-sql-languages` classifies `JOIN`, `AND`, `OR`, `NOT`, `IN`, `LIKE` and `UNION` as `operator.keyword`, not as keywords, so they come out as `operator.keyword.sql`. Theme rules match by dot segments: `operator.sql` is a _sibling_ branch and never applies, the token falls back to the generic `operator` rule. The same code had worked with Monaco's built-in SQL grammar, whose names differ — swapping a tokenizer silently invalidates every `*.sql` theme rule.
- **Never assert beyond the schema that was actually loaded.** `getAllColumns` and the table list are filtered on the current database, so `other_db.users` cannot be verified. Coloring it anyway would mark typos as valid; the rule is to leave unverifiable names alone. Same reasoning for column warnings: only qualified references to a resolved table are checked, never bare columns (subqueries, CTEs, expression aliases).
- **Do not derive the caret's qualifier from `getSuggestionAtCaretPosition`.** It reports a `column` context only while the name is still empty — `alias.na` becomes a `function` context, and inside a `WHERE` it can return nothing. Read the qualifier from the model instead (`getWordUntilPosition` plus the preceding character). Symmetrically, the alias table must be extracted from the **whole** model, not from the text before the caret: `SELECT e.| FROM employee e` needs the `FROM` clause that follows.
- **A whole-line decoration on `base01` erases Monaco's current-line highlight.** Corrected by the user (2026-09-02) right after the current-statement band landed: `editor.lineHighlightBackground` is already `base01`, and the decoration is painted in the same `.view-overlays` layer *before* `.current-line`, so an opaque band on that slot simply covered it — "le highlight souris n'affiche plus rien". A decoration that spans lines must stay **translucent** (the band is `base02` at 30 %), and the signal it carries has to live somewhere the caret line does not compete: a 3 px bar in the line-decorations margin. Two mechanics to know, both found by reading the DOM rather than guessing: overlay z-order follows DOM order, and Monaco writes `left`/`width` **inline** on a margin decoration — a class cannot resize it, so draw the bar as a `border-left` (a `border-right` lands past the margin's width and is clipped away, invisible with nothing in the console).
- **`monaco-editor` decorations take class names, never colors — the `borderColor` of VS Code is the extension API, not Monaco.** The user pushed back on the gutter div (2026-09-02), reasoning from `vscode.window.createTextEditorDecorationType({ borderColor, borderWidth })`; that API belongs to the workbench, which compiles those values into generated CSS classes, and none of it ships in the package — `registerDecorationType`, `setDecorationsByType` and `gutterIconPath` match nothing under `esm/` or `min/`, while a control term (`linesDecorationsClassName`) does. `IModelDecorationOptions` only takes a color on `overviewRuler.color` and `minimap.color`. What Monaco *does* theme itself is `editor.lineHighlightBorder` (it emits `.current-line-exact { border: 2px solid … }`, `viewParts/currentLineHighlight`, and only when the theme defines it explicitly) — the caret line, not an arbitrary range. And `linesDecorationsClassName` is not a workaround: it is Monaco's own per-line gutter channel, the one VS Code draws breakpoints and git markers with. Putting the border on the whole-line `className` instead does not work — that element starts at the first character (both measured at x=84), so the bar renders under the text.
- **Verify syntax highlighting through computed styles, not screenshots.** `getComputedStyle(span).color` over `.view-line span span` gives the exact token colors. And pick a theme whose slots differ: Dracula defines `base0A === base0C`, so tables and aliases render identically there and a screenshot proves nothing.

## Electron dev tooling

- **Only ever run ONE app instance while measuring startup or extension behaviour.** Debugging the React DevTools extension (2026-08-18) produced contradictory results — the same code "worked" at 11:15 and failed at 11:19 — because several `yarn start` instances were alive at once, all sharing the same `userData` profile and extension store. It led to a confidently wrong A/B conclusion. Kill every instance (`Get-Process electron | Stop-Process`) before each measurement, and repeat a run before calling a race fixed.
- **`electron-devtools-installer` never refreshes its cache.** `downloadChromeExtension` returns early when `<userData>/extensions/<id>` exists, so a CRX downloaded years ago is reused forever — that is how React DevTools 5.0.2 (March 2024) ended up facing React 19 and reporting "Unsupported React version detected". `installReactDevToolsExtension.ts` now forces a re-download when the cached `.crx` is older than 30 days.
- **React DevTools v7 needs its service worker started before the first navigation.** The devtools hook is no longer a static content script: the MV3 service worker registers it via `chrome.scripting.registerContentScripts`, and Electron only puts that registration in force once the worker runs. Hence the awaited `session.defaultSession.serviceWorkers.startWorkerForScope(extension.url)` before `createWindow()` (~1-2 s of dev startup). Reloading the window does **not** repair a document that loaded without the hook: Vite's react-refresh then owns `__REACT_DEVTOOLS_GLOBAL_HOOK__` as a non-configurable property and `installHook.js` gives up. The session that downloads the extension is therefore always hookless — only the next start works.

## Electron dev loop

- **The main process is NOT hot-reloaded — an IPC contract change needs a full app restart.** `@electron-forge/plugin-vite` rebuilds `.vite/build/main.js` on save (watch mode) but never relaunches the running Electron process, while the renderer picks the change up through HMR. A renderer talking to a main process from an older build produces symptoms that look nothing like the change: making `setPanelSize` answer with the configuration (2026-08-24) had the fresh renderer receive `undefined` from the stale handler, `setConfiguration(undefined)`, and the whole app blank out with `ConfigurationContextProvider` as the last node in the tree. Before debugging a bizarre IPC symptom, restart the app; and when a channel's return value changes, say so.
- **A renderer must never let an IPC answer erase the UI.** The provider renders `null` while it has no configuration, so a single channel answering with nothing unmounted every consumer. Guard the state setter and keep the previous value instead — an unpersisted setting is a far better failure than a blank window.

## Component design

- **`styled(AnotherStyledComponent)` composition folds into one DOM element — it is not the "+15% per extra styled-component" the TableGrid benchmark warns about.** Verified in the browser: chaining `styled(BaseCell)` for `NullSpan`/`StringSpan`/`NumberSpan`/etc. in `Cell.tsx` still renders a single `<div>` with two class names, no wrapper. The benchmark's cost applies to an _additional element actually mounted_ per cell (a wrapper span, an antd component), not to how many `styled(...)` calls sit in the chain that produces that one element. Don't collapse per-variant styled components into one with a color prop to "save" a cost that composition never incurs.
- **In `TableGrid`'s virtualized body, a per-cell closure (e.g. `onDoubleClick={() => ...}`) is effectively free — wire it in the scope that already holds the data, not via DOM delegation on a parent (`<tbody onDoubleClick>` + `data-*` attributes + `closest()`).** The real cost ranking measured in this codebase is antd components (~+120%) > styled-components per extra rendered element (~+15%) > plain closures/components (~0%). Delegation trades a free in-scope lookup for DOM traversal to reconstruct what was already known — only worth it if the per-item cost would otherwise be a mounted component.
- **Both pointer gestures of a cell belong on the `<td>` of `BodyRowInner`, not on what the cell renders.** `onDoubleClick` used to be threaded down to `GridCell` → `Cell` → `CellShell`, so it landed on the value `<div>`; `onContextMenu` was then added to the `<td>`, and the user caught the discrepancy (2026-08-27). Both now sit on the `<td>`, which fixed a latent gap and removed plumbing: the `<div>` covers neither the cell's 16 px of padding nor the foreign key `<a>`, so double-clicking either did nothing. `BodyRowInner` has `column`, `value`, `original` and `row.index` in scope, so the closures cost the same there — and `Cell.tsx` went back to rendering values and nothing else (no `onDoubleClick` prop, no `...rest` spread through every per-type renderer). Rule: the cell shell owns the gestures, the cell content owns the rendering.
- **An `<svg>` sized to fill its box still reserves the line box's descender space under it — make it `display: block`.** The chart panel flickered its scrollbars on every frame (2026-08-31). nivo's `Responsive*` measures `ChartArea` and renders the `<svg>` at exactly that height (798px measured), but the svg is `display: inline`, so its wrapper came out at 804px. Those 6px overflowed the result panel's `overflow: auto`: the vertical scrollbar took 15px of width, the svg — measured a frame earlier, so still at the old width — then overflowed horizontally, that scrollbar took 15px of height, nivo re-measured smaller, both scrollbars vanished, and the cycle restarted. Measured in Storybook against headless Chrome: 44-49 state flips per 50 frames before, 0 after `svg { display: block }`, at every width. Two general points: **a self-measuring component inside an `overflow: auto` ancestor is a feedback loop waiting for a trigger** — any phantom pixel closes it, because a scrollbar changes the very size the component measures; and `scrollbar-gutter: stable` on the scroller *stops the oscillation* but is the wrong fix, since it leaves the 6px overflow and so a scrollbar permanently parked over nothing. Find the phantom pixels instead: walk the subtree comparing each element's `getBoundingClientRect().bottom` against the scroller's content bottom, and fix the deepest one that overflows.
- **Adding a variant to a styled-component family: extend the family, don't refactor it into fragments.** Corrected by the user (2026-09-09) while giving `TabStrip` a `NavLink` item: « à mon avis tu factorises trop les styled component ». To share the item styles I had split the single `item` block into `item` + `activeItem` + `failedItem` + `itemState` + `linkItem` and rewritten the two existing items in terms of them — five names and a cascade-order comment where the original had one block and one ternary, for a variant that in the end only needed `css<ItemProps>` → `css<Partial<ItemProps>>` so it could declare neither flag. Rule: measure a factorisation by what the *diff* removes, not by how few characters repeat, and never rewrite the styling of components that were not the point of the change. (The variant then moved out of `TabStrip` entirely — see the switch below — which is the other half of the lesson: a different *look* is a different component, not a parameter on this one.)

- **A font size in a styled-component is a value of the theme, like a colour or a space — the app is meant to let the user choose it.** Corrected by the user (2026-09-09) on a `font-size: 11px` written in `ViewSwitch`: « il faudrait que ça hérite de la taille de base du thème car à terme j'aimerai pouvoir choisir la font size dans les paramètres (pas tout de suite mais en prévision) ». So the type scale now lives in `renderer/theme` as one `BASE_FONT_SIZE` plus the two steps derived from it (± 2, the way antd derives `fontSizeSM` / `fontSizeLG`), exported twice for the two consumers that cannot share a form: `fontScale` in numbers for antd's tokens, `fontSize` in `px` strings for CSS. `ThemeContext` feeds both the `body` rule and the tokens from it, so the base is stated once. **A design constraint the user states as "later" is a constraint on the shape of the code now**: the size had to stop being a literal *before* the setting exists, or the setting would mean a sweep. The sweep converted only the literals that were exactly a step of the scale (11 / 13 / 15, eleven of the sixteen `font-size` in the renderer) — 10, 12, 14 and 17 stay put, because folding them in is a design call on the scale, not a substitution.

- **A control takes the look of whatever already sits in that place, and each look is its own component.** Same review (2026-09-09): the table's Data/Structure navigation was built as a `TabStrip` — hairline separators, 6px accent pip — but it lands at the right of a result region's header, where the SQL page already has the Data/Chart `Segmented`: « il faudrait plutôt reprendre le style que l'on a dans /sql […] car c'est le même endroit (au dessus d'une liste de résultats). Si besoin tu peux là en faire un composant style button group différent ». So `Style/ViewSwitch.tsx` (a framed run of `NavLink` segments, the current one filled) sits next to `Style/TabStrip.tsx` (a run separated by rules, the current one pipped), and the frame has two named looks instead of one component with a `$variant` prop. Getting the look right means *measuring the original*, not eyeballing it: the antd control's computed styles read through CDP (21.6px tall, 1px `base02` frame, 20px segments, 11px uppercase at 0.06em, `base04` fill on `base00` text) then rebuilt from the accessors the `Segmented` tokens themselves use, so the two switches move together. Pixel-for-pixel except antd's 7px segment padding, which stays `space.sm` — a raw pixel value in a styled-component is worse than a 1px difference nobody can see.

- **An ornament of one cell does not travel through the grid's rows as a prop — it lives in its own hook and lands on the DOM element the event already handed over.** Corrected by the user (2026-09-07) on the flash of a written cell: « on peut mettre ça dans un composant ou un hook séparé ? là ça commence à être compliqué dans BodyRow et TableGrid pour un truc annexe ». The first version held a `writtenCell` state in `TableGrid`, passed it to `TableBody`, resolved a `writtenColumnId` per row, added it to `BodyRow`'s props and `memo` comparison, and set `data-written` on the `<td>` — six touch points in the hot path for a 1.6 s tint. The second (`useWrittenCellFlash`) remembers the `<td>` from `event.currentTarget` of the double-click and sets the attribute on it once the write succeeds; `TableGrid` gains one hook call and one line, `BodyRow` passes the element it already has. Same family as `setTitleIfTruncated`, which sets `title` on hover rather than at render: **a transient, presentational mark on a single element is set imperatively on that element, with its CSS (`css` fragment) and its timing in one module — the declarative tree is for data, and every prop added to `BodyRow` is a comparison paid by every row.**

## React / antd

- **`useState` whose setter is never used is not a way to freeze a value — drop it and read the value directly.** Corrected in `usePanelSize` (2026-08-24): the initial panel size was held in a `const [defaultSize] = useState(() => ...)` to "pin" it at mount, but the source (`configuration.panelSizes`) is never pushed back into the context state, so there was nothing to pin. A lazy `useState` only earns its place when the value it derives from _does_ change and the component must ignore that change — and even then, say so in a comment.
- **A value written through a context and read back through it must go through the context state — no shortcut to the main process.** `setPanelSize` was wired straight to `window.config.setPanelSize`, bypassing `willChangeConfiguration`, on the theory that skipping the state avoided re-renders. The context's `configuration` then kept the value loaded at startup, and every remount (`<TableLayout key={whereFilter}>`, a table change, re-entering the SQL page) restored the panel to its pre-drag size — the feature only appeared to work after a restart. The write-only setters (`setActiveDatabase`, `setActiveTable`, `setTableFilter`) get away with the shortcut because their readers are route loaders that re-ask the main process; the moment a value is read from `useConfiguration()`, the state is the single owner. Note the reasoning error that locked it in: a context value change **re-renders** consumers, it does not remount them — Monaco and the grid are not recreated.
- **Never persist a pixel size that will be replayed on another screen.** A panel width dragged on a wide display and restored on a laptop can exceed the container; antd's `autoPtgSizes` then scales that panel to 100% and gives its sibling 0px, and its `min`/`max` are ignored on that path (`sizeUtil.js`, "fill if exceed" branch), so no CSS and no `max` prop can save it. `usePanelSize` stores a **percentage of the splitter** instead — a ratio cannot overflow, and it keeps the chosen layout at any window size. Pixels remain fine for a first-run default, which is small by construction. Two corollaries, both learned the hard way (2026-08-24) when the app was relaunched on a config holding `{tableList: 389}` written minutes earlier: **a persisted value carries its unit** (`'32.5%'`, not `32`), so a value written by an older build is recognizable and can be rejected instead of reinterpreted; and **"not released yet" is not "no migration needed"** — the user's own machine already holds yesterday's format the moment they run the app once.
- **A zero-sized anchor is invisible to rc-trigger, and its popup never gets positioned.** Building the grid's context menu (2026-08-27) the antd `Dropdown` was hung off a `position: fixed; width: 0; height: 0` div placed at the click. The popup mounted, held the right items, and stayed parked at its pre-alignment `top: -1000vh; left: -1000vw` — nothing in the console. `useAlign` refuses to align when `isVisible(target)` is false (`@rc-component/trigger/lib/hooks/useAlign.js`, `scaleX === 0 || scaleY === 0 || (isDOM(target) && !isVisible(target))`), and `@rc-component/util`'s `isVisible` reads `offsetParent` — **null on a fixed element** — before falling back on the size of the bounding rect. One pixel plus `pointer-events: none` fixes it. Two general points: a popup stuck at `-1000v*` means "align never ran", not "wrong placement"; and an invisible anchor still has to be *measurably* there.
- **A controlled antd `Dropdown` should still declare `trigger={['contextMenu']}`.** The trigger list is not only about opening: rc-trigger derives `clickToHide` from it (`hideActions.has('click') || hideActions.has('contextMenu')`), which is what registers the window-level `mousedown`/`contextmenu` capture listeners that dismiss the popup, and what makes scrolling close it. Declaring it while driving `open` yourself keeps the dismissal behaviour and costs nothing — the trigger element (a zero-area anchor) never receives those events itself. It also explains why right-clicking a second cell works: the window `mousedown` closes the menu, and the `contextmenu` that follows reopens it at the new point.
- **`Typography.Text keyboard` is not usable here: its `<kbd>` hardcodes `rgba(150,150,150,.06)` / `rgba(100,100,100,.2)` and a 3px radius** (`typography/style/mixins.js`), outside any token — two of the design rules broken at once (palette-only colours, radius 0). Tried during the antd sweep (2026-09-04) and reverted: the shortcut hints stay on our `<kbd>` styled-component (mono, 11px, 75 % of the text colour). Check a mixin for hardcoded values before swapping a styled element for an antd typography variant.
- **antd 6 declares its own CSS variables on the component's root element — a `var()` passed as a token is resolved *there*, not where a descendant re-points it.** Found while tinting the title bar (2026-09-09): `Layout.headerBg: 'var(--frame-bg)'` produced `--ant-layout-header-bg: var(--frame-bg)` on the **`Layout`** element, one level above the `header` that declared `--frame-bg`, so the fill stayed base00 while every text colour — whose tokens (`Button.textTextColor`) are declared on the button itself, inside the bar — did follow. So: a token may carry a `var()` only when the element antd declares it on is inside the scope that sets it. Read the generated rule (`document.styleSheets`, filtered on the component's class) before trusting a token to inherit; where it cannot, paint the property in the styled-component with a doubled `&&` — `:where(...)` gives antd's own selector zero specificity, so one extra class is enough to outrank it.
- **Never style antd internals through their `.ant-*` class names.** Corrected on the SQL page (2026-08-24), where a `styled(Form.Item)` reached into `.ant-form-item-row`/`-control`/`-control-input`/`-control-input-content` to pass a height down. Those class names are private and change between versions. Look for the escape hatch antd provides instead: `Form.Item`'s `noStyle` renders the bare control with no wrapper at all, and antd 6 components expose semantic `classNames`/`styles` maps for the rest.

## ORM / framework conventions

- **Don't special-case one ORM's convention when it doesn't generalize.** Considered and rejected: parsing Doctrine DBAL's `(DC2Type:json)` column-comment marker to decide JSON rendering. Doctrine is essentially alone in encoding type metadata in SQL comments (DBAL 2/3 introspects a live schema with no code-side model; DBAL 4 dropped the markers for platform type maps). Other ORMs (Rails, EF Core, Prisma, Django, SQLAlchemy, Hibernate, TypeORM) keep a code-side schema and never needed this. A framework-specific heuristic here is a dead end for every other ORM/raw-SQL user and doesn't even survive Doctrine's own next major version.
- **Prefer detecting behavior from the value itself over trusting metadata from a specific convention.** A column's declared SQL type can lie about the data (JSON-in-text-column is common; MariaDB's `JSON` type is itself just an alias for `LONGTEXT` + a `CHECK` constraint, so even the "real" type can mislead). `cellValueToText` (`src/renderer/component/cellValueToText.ts`) tests the value at runtime — starts with `{`/`[` and `JSON.parse` succeeds — rather than branching on column comments or ORM markers. Generalize by capability, not by vendor convention.
- **`Types.JSON` is MySQL-only — don't propose `CAST(x AS JSON)` as a repro here.** The dev database is MariaDB, where `JSON` is an alias for `LONGTEXT` + `CHECK (json_valid(...))`: the server announces the column as `LONG_BLOB`, `JsonCell` is never reached, and `CAST(x AS JSON)` is a syntax error (1064) since `JSON` is not a cast target. A review comment (PR #152) suggested exactly that cast to exercise the JSON path and the user hit the error. Before writing a repro query, check which server the feature actually needs, and say so in the comment.

## Comments

- **A comment states what the code cannot; it does not narrate the reasoning that produced it.** Corrected by the user (2026-08-29) — « pas besoin de raconter ta vie dans un commentaire de code » — on a nine-line docblock above `isNewerVersion` that argued why a library beat a hand-rolled comparator, recounted the bugs the hand-rolled one had, and only then reached the one fact a reader needs: `compareVersions` throws on what it cannot read, hence the `validate` guard. That fact is a single line, and it was the only line worth keeping. Same treatment across `updateCheck.ts`, `installSource.ts`, `VersionBadge.tsx` and `useUpdateStatus.ts`: `/** \`net.fetch\`, not Node's: it honours the system proxy. */` replaced four lines about corporate machines. Tests to apply before writing one: is it deducible from the signature or the next statement (`Pure, so it can be exercised…` above a function taking its input as a parameter — cut); does it justify a decision rather than explain the code (that belongs in the commit message, the PR, or `docs/` — cut); does it describe a defunct alternative (cut). What survives: a non-obvious constraint (`a Flatpak also has a /usr, so the env vars must win`), a magic value's meaning (`403 is the anonymous rate limit`), a deliberate-looking-like-a-bug choice (`unknown` is a real case, not a detection failure).

## Reporting to the user

- **A base16 slot name is never written alone — its role follows in brackets.** Corrected by the user (2026-09-04) on the design-system recap: « base07 ça ne me parle pas ». Write `base07 [texte d'emphase]`, `base0D [accent]`, `base02 [fond de sélection]`, `base00 [fond]`, `base03 [filets et texte secondaire]`, every time, in the message and in review notes. The slot table of DESIGN.md is the reference for the role words.
- **A library internal is explained by what it does to the screen, with the before/after values.** Same recap: "antd's dark algorithm re-tunes colorPrimary" and "antd derives 10 and 14 from 13" were not understood. Say instead: "antd recomputes the accent for dark themes, `#36f9f6` came out as `#31d7d4`, so the Run button was not the palette's colour; a small function puts it back", and "from a 13px body antd computes 10px small and 14px large; the design wants 11 and 15, so both are set by hand". The token name can follow in a code span, it is not the explanation.
- **No design jargon in a message: « handoff », « mock », « slot » are words the user had to ask about.** The user asked « c'est quoi le handoff ? » (2026-09-04) after a recap called the design folder that way three times. Say « le dossier de design que tu m'as donné », « la maquette », « la couleur base07 [texte d'emphase] ». The jargon can stay in code comments and commit messages, which name files, never in what the user reads.
- **Never an antd colour: every colour on screen is a slot of the palette.** Stated by the user (2026-09-04) when the SQL error became an antd `Alert` in antd's own red: « on ne doit jamais utiliser les couleurs antd, toujours celles du thème ». The semantic seeds are mapped in `ThemeContext` (`colorError` → base08, `colorWarning` → base0A, `colorSuccess` → base0B, `colorInfo` → base0C, `colorLink` → base0C) and pinned through the dark algorithm by `keepPalette`, which antd would otherwise re-tune. Before shipping any antd component with a state colour (Alert, danger Button, validation, Tag, Badge), check which seed it reads and that the seed is mapped. The rule is about the *source* of a colour, not about using it raw: a colour may be derived from a slot to emphasise or soften it — the border and the background of an alert must come from the same base08 [errors], and one can be a tint or a mix of the other (what antd's `colorErrorBorder` / `colorErrorBg` derivations do from the seed, or a `color-mix()` of a slot with the background, as the grid's hover does with base02). What is forbidden is a colour whose base is not a slot of the palette.

- **Our own elements are styled-components, never inline `style` objects.** Corrected by the user (2026-09-04) after point 6 of the antd sweep had turned `Written` into `<div style={{ padding }}>` and the layout groups into `Flex` with `style={{ minWidth: 0 }}`: « préfère quand même styled component plutôt que des styles inline ». Replacing a styled div by an antd `Flex` is only a gain when no `style` prop is needed to finish the job; otherwise the styled div was the right tool. An inline `style` (or `styles`) is fine where it is the API of an antd component: `Form.Item style={{ marginBottom: 0 }}`, `Form styles={{ label }}`, `Segmented styles={{ root }}`.
- **The selection motif is not a detail to give up: the 3px accent rule stays on the left, on our `TableLink`.** Tried and refused by the user (2026-09-04): antd's Menu draws its bar on the right only, in `inline` mode only, and in the *selected text colour* — getting an accent bar meant an accent table name. The same session also refused turning the "Go to table…" button into a read-only `Input` (« sémantiquement, c'est quand même plus un bouton »): a control keeps the element its behaviour calls for, whatever the mock draws.
- **A detail of the mock that costs an override of antd is a detail to give up, not to fight for.** Said by the user (2026-09-04) about the Run button's divider: « j'ai validé le design, mais on peut changer légèrement si ça implique de faire trop de trucs custom ». The 35 % hairline between the two segments had cost a plain row and a `styled(Button)` border override; antd's `Space.Compact` draws its own divider in the hover colour, and that is what stays. When a mock detail needs a `styled(antdComponent)` override or a wrapper of our own, name it as a trade-off in the recap and default to antd's rendering.
- **When two sources of the design folder disagree, present the choice as a decision with the visible consequence of each option.** Flagging "base07 per the table, not base05 per the snippet" left the user asking « que dois-je décider ? ». Give: what each option looks like on a dark and a light theme, which one the mock shows, and a recommendation.

## Navigation

- **A navigation is a `Link`, never an `onClick` that calls `navigate`.** Corrected by the user (2026-09-04) on the connections strip, which had turned the previous `Link`s into buttons: « je préfère des liens, même si on n'est pas sur du web ». A link keeps the router's semantics (href, middle-click, focus order, `aria-current`) and says where it goes; a button that navigates hides it. Reserve `navigate()` for what follows an action (a form submitted, a filter built).

- **The active state of a link is `NavLink`'s job, not a `useMatch` with the route pattern retyped.** Corrected by the user (2026-09-09) on the table's Data/Structure tabs, whose pip came from `useMatch('/connections/:connectionSlug/:databaseName/tables/:tableName/structure')`: « normalement react-router a déjà un truc automatique pour l'état "actif" ». `NavLink` matches its own `to` against the location, adds the `active` class and sets `aria-current="page"` itself, and its function children hand `isActive` over for the pip — so the pattern is written once, in the router. Two details that make it a drop-in: `end` is required wherever a longer path nests under `to` (without it the data tab stays active on the structure page), and matching ignores the query string, so a filtered table keeps its tab. A `useMatch` on a pattern *copied from `app.tsx`* is duplicated route knowledge that can drift with nothing failing. `active` passed by hand stays legitimate only when something other than the URL decides — the connections strip, whose active item comes from the open connection.

- **`useNavigation()` is not `useNavigate()` — say so when proposing it.** The plan for the connection spinner said "l'état d'attente est lu avec `useNavigation()`" and the user pushed back (2026-09-08): « on n'utilise pas `useNavigation`, on garde le `Link` ». The two names differ by one letter and mean opposite things: `useNavigate()` returns an imperative navigator (the thing [[feedback-links-over-navigate]] rules out), `useNavigation()` is read-only state about the navigation the router is already running, and the `Link` stays untouched. Naming the hook is not enough — spell out that nothing becomes imperative. Related: react-router offers no "on click" hook to hang a pending state on; `useLinkClickHandler` builds a link component, it does not observe one. And a hand-rolled `onClick` + `useState` is worse than it looks, because nothing clears it when the navigation *fails*.

## Renderer / dependencies

- **Never import from `mysql2` in renderer code.** `mysql2` is CommonJS and breaks in the renderer bundle. Import type-only symbols from `mysql2/promise` with `import type`, and runtime values like `Types` from the legacy `mysql` package (see `src/renderer/component/Cell.tsx`).
- **Dependency size is NOT a criterion here — this is an Electron app, it ships its own runtime.** Stated by the user (2026-08-24) after I twice hedged about the ~400 KB of `intl-messageformat`, and even offered to back the ICU work out over it. Don't weigh a dependency by its weight, don't put a size caveat in a PR description, and don't propose a worse design to save kilobytes. Judge a dependency on whether it is the right tool, whether it is declared, and whether the need is real.
- **When a library replaces hand-written code, delete that code's tests with it.** Corrected by the user (2026-08-29) after `isNewerVersion` was swapped from a hand-rolled triple comparator to `compare-versions`: I kept the twelve tests I had written for the old implementation. They no longer tested anything of ours — the wrapper is `validate()` then `compareVersions() > 0`, and every case they exercised (prerelease ordering, `1.10.0` vs `1.9.0`, the `v` prefix) is the library's own test suite, maintained by the library. Keeping them means re-asserting a dependency's behaviour on every CI run and pinning us to it. Same rule as the `escapeSqlString` → `mysql.escape` swap above: the replaced module goes, and its tests go with it. Keep a test only for behaviour that is genuinely **ours** and not obvious — a guard the library does not provide, a mapping we decide. What survives here is `installSource.test.ts`, which tests our own detection, not anyone's library.
- **And reach for the library earlier.** The hand-written comparator shipped two real bugs in ~30 lines — `1.0.5` read as newer than `1.2.0`, and two prereleases it refused to order. The reason given for writing it by hand (`semver` was only a transitive dependency and the worktree had a symlinked `node_modules`) was a tooling accident, not a design argument, and it silently outlived the situation that produced it. When the justification for hand-rolling is circumstantial, re-check it before the code lands.

- **Do not add a date library, and question any dependency reachable only through antd.** Building the cell editor (2026-08-24) I reached for antd's `DatePicker`, which drags in `dayjs`; the user rejected it. Read together with the rule above, the reason was never size: (1) a `dayjs` that resolves only because antd depends on it is an **undeclared** dependency; (2) the need was **imaginary** — a MySQL `DATE`/`DATETIME` is a _wall clock_ with no offset, so `<Input type="datetime-local">` plus the punctuation swap of `src/renderer/component/CellEditor/dateTimeText.ts` (`2026-01-15 10:30:00` ⇄ `2026-01-15T10:30:00`) does the job with no library at all. Parsing the literal into a `Date`/`Temporal.Instant` would attach a time zone the stored value never had and shift it on the way back. Reach for a date library only when actual calendar arithmetic is needed.

## i18n

- **Never build a translation key at the call site.** `t(\`cell.detail.readOnly.${reason}\`)`was rejected (2026-08-24): a key that only exists once a variable is interpolated is invisible to any extractor, unverifiable against`locales/type.ts`, and impossible to grep. One message with several variants stays **one key** holding an ICU `select`, chosen at runtime from the variable: `t('cell.detail.readOnly', { reason })`against`'{reason, select, binary {…} other {…}}'`. `i18next-icu`+`intl-messageformat`are installed and wired in`src/i18n.ts`. ## SQL semantics

- **A `PRIMARY KEY` column is never NULL — MySQL forces `NOT NULL` on all of them.** So the `WHERE` that targets a row uses plain `=`; the null-safe `<=>` is for the _guarded_ column only, where NULL is a real value. Writing `<=>` on the key was flagged (2026-08-24) precisely because it made a reader wonder when a key could be NULL. `getPrimaryKeys` reads `SHOW KEYS … WHERE Key_name = 'PRIMARY'`, never a unique index, so there is no case to hedge against. Encode the impossibility in the type too: `PrimaryKeyValue = Exclude<SqlBoundValue, null>`.
- **Bind query parameters by name (`:databaseName`), never by position (`?` + an array).** Asked for by the user (2026-08-24) on the `Database name is required` fix, and applied to every query built in the main process. `mysql2` supports it: `namedPlaceholders: true` in the query options — it delegates to the `named-placeholders` package, which rewrites `:name` to `?` and reorders the values itself. What it buys is not brevity but the disappearance of a whole failure mode: `buildUpdateCellQuery` used to return `[newValue, ...primaryKeyValues, ...(guard ? [originalValue] : [])]`, an order that had to be read against SQL assembled a few lines above, and that `buildReadCellQuery` deliberately built _differently_ (`[originalValue, ...primaryKeyValues]`). Values now travel as `SqlBoundValues = Record<string, SqlBoundValue>` and a conditional clause becomes a conditional _key_, not a conditional position. Three things to know before reaching for it, all checked against the package rather than guessed:
  - **Ask for it per query, never on the connection.** `namedPlaceholders: values !== undefined` in `#executeQuery` (`src/sql/index.ts`) keeps the rewriter away from the raw SQL of the editor, because **it does not know backticks**: a `:` inside a quoted identifier (`` `we:ird` ``) is read as a parameter and corrupts the statement — ``SET `we:ird` = :newValue`` comes out as ``SET `we?` = ?`` with a `null` bound in front. A loud server error rather than a wrong write, and a colon in a column name is vanishingly rare, but there is no reason to expose queries we did not build to it.
  - **What the rewriter does _not_ trip on** — checked against `named-placeholders@1.1.6`, the version `mysql2` loads, after a first version of this lesson claimed the opposite (2026-08-24): its tokenizer skips string literals _and_ comments (`--`, `#`, `/* */`), so `SELECT 1 -- TODO: something` comes back untouched. Don't write a rule about a dependency from the shape of its regex; run it.
  - **A name that does not match is silent, in both directions.** A parameter the statement names and the object does not hold is bound to `null` — no throw, `('UPDATE t SET a = :a WHERE id = :missing', {a: 1})` yields `[1, null]`; a key the statement does not name is dropped. Positional binding at least threw on a count mismatch. So the builders are tested on the exact `sql`/`values` pair, plus one `describe.each` over every shape asserting that the `:names` of the statement and the keys of the object are the same set (`buildUpdateCellQuery.test.ts`) — verified by mutation: renaming one parameter fails 9 tests.
- **Escape every identifier that is interpolated into SQL, on both sides of the IPC.** `escapeIdentifier` (`src/sql/escapeIdentifier.ts` — its own module, since it serves far more than the cell update it was born in) is imported by the main process _and_ by the renderer, which builds `USE …` and `SELECT * FROM db.table` itself. An unescaped name is not a theoretical injection worry here so much as a plain bug: `SHOW TABLE STATUS FROM my-db` and `USE my-db` are syntax errors, and a dash in a database name is common. Values are bound, identifiers are quoted; the only thing sent as written is SQL the user typed (the `where` filter, the editor).
- **Types describing an _action_ do not belong in `src/sql/types.ts`.** That file holds the shapes MySQL answers with (`RowDataPacket` derivatives). A command and its outcome — `UpdateCellRequest`, `UpdateCellOutcome` — live in their own module next to the code that serves them (`src/sql/updateCell.ts`), together with any result row that exists only to serve them.

## Enums over string unions for external vocabularies

- **A closed set of values coming from outside the code gets a real enum, not string literals.** Two places were corrected (2026-08-24): the `DATA_TYPE` values of INFORMATION*SCHEMA, now `DataType` in `src/sql/dataType.ts`, and the reasons a cell is read-only, now `NotEditableReason` in `src/sql/columnEditing.ts` (which doubles as the ICU selector of its message). Same for `ValidationError` in `CellEditor/editableValue.ts`. Values read from the database stay typed `string` and are \_compared* against enum members — narrowing them to the enum would lie, since a server can answer something absent from the list (MariaDB's `inet6`, `uuid`).
- **The rule covers internal discriminants too, not just values crossing a boundary.** `EditorKind` was left as a string union with bare `case 'json':` labels and was corrected (2026-08-24): it is an enum, and `CellEditor` switches on `EditorKind.Json` & co. A closed set of names gets an enum, wherever it comes from.
- **The rule covers the driver's _functions_ too, not just its constants — and `mysql` is importable from the renderer, so "mysql2 is unavailable" is never the excuse.** Corrected by the user (2026-08-27): `escapeSqlString` was a hand-written module reimplementing the escape table of a MySQL string literal, justified by a comment claiming the renderer could not reach the driver. But `mysql` (v2) is a **declared** dependency, is already imported for `Types`, and exports `escape` — which delegates to `sqlstring`, the very package `mysql2` escapes with. The hand-written table was byte-for-byte identical to theirs, verified case by case. It is gone; `escape` is called directly, with no wrapper module and no tests of its own (testing a dependency's escaping is not this repo's job). Two things to know before calling it: `escape` is typed `(value: any)` and only behaves as "quote this literal" for a **string** — a `Date` comes out shifted into a time zone the stored value never had, an object comes out as a `SET` clause, and the object branch calls `Buffer.isBuffer`, which throws in the renderer (`Buffer` is undefined there — checked in the browser). A string takes the `default` branch and touches none of it, which is why `cellValueToSqlLiteral` decides the form of every non-string value itself before reaching `escape`.
- **The symmetric question has the opposite answer: `escapeIdentifier` stays hand-written, and the reason is behaviour, not reachability.** Asked right after the correction above (2026-08-27), and checked rather than assumed: `mysql.escapeId` _is_ reachable from both processes, and importing `mysql` costs 1.7 ms and one module, so neither "unavailable" nor "too expensive" holds. What holds is that `escapeId`'s default reads a `.` as a **qualifier separator** (`escapeId('a.b')` → `` `a`.`b` ``), so all eleven callers — each passing a single name and assembling `` `db`.`table` `` themselves — would have to remember `forbidQualified = true`, and forgetting it mangles a dotted name in silence. The user pushed back that a `.` or a backtick cannot appear in a table name, so it was **checked against real servers** (MySQL 8.4 and MariaDB 11.4 in podman) rather than argued: `` CREATE DATABASE `my.db` ``, `` CREATE TABLE `a.b` ``, a `` `c.d` `` column and a `` `we``ird` `` column are all accepted on both — a quoted identifier takes the whole BMP, and it is only the *file name* on disk that encodes the dot (`my@002edb`). `` SELECT * FROM `my.db`.`a.b` `` reads the row; the qualifier-splitting form is ERROR 1064. Lesson within the lesson: a claim about what a server accepts costs one container to verify, and both of us were reasoning from memory. and `escapeId('')` answers with two bare backticks, invalid SQL with no complaint, where the `invariant` names the bug (the failure mode behind PR #154). Both differences are now pinned by tests. The general rule: delegate when the duplicated thing is **driver policy that can drift** (a 9-entry escape map, `\Z`, the `NO_BACKSLASH_ESCAPES` assumption); keep it when it is **one character fixed by the grammar** and the driver's version needs an option and a guard bolted on to match.
- **`typeof x === 'undefined'` is ES5 habit — write `x === undefined`.** `typeof` is only needed for an identifier that may not be _declared_; for a variable, a parameter or a property it is noise. Applied across `src/` (2026-08-24).
- **Check whether the driver already exports the constants before writing a list.** `mysql2` (and `mysql`, the one the renderer may import) exports `Types` — the **wire protocol** field types. That is a _different_ vocabulary from INFORMATION_SCHEMA's `DATA_TYPE`, and mixing them up is easy: the protocol collapses `TEXT`/`BLOB` into one type and announces an `ENUM` column as a plain string. Rule: read `Types` wherever the protocol can answer (numbers, dates, JSON — this also keeps `resolveEditorKind` in step with `Cell.tsx`), and `DATA_TYPE` only where it cannot (`enum`/`set`, `text` vs `blob`). Do not hand-maintain a parallel list of either.

## IPC

- **The context bridge rebuilds an `Error` from `name`, `message` and `stack` alone — every property added to it is dropped, in silence.** Found by measuring rather than reading (2026-09-08): a connection failure tagged in the main process arrived in the renderer with `Object.keys(e)` empty, so the error page fell back to its generic branch. That is exactly why `decodeError` returns a plain object literal for `sqlError` instead of an `Error` — a plain object is cloned whole. So: anything a renderer must *read* off an error travels as a plain object, and only the last hop (a `throw` inside a route loader) may be error-shaped. Check a tag survived with `window.sql.x().catch(e => Object.keys(e))` in the page, not by reasoning about the encoder.
- **Channel enums must stay in dedicated `src/preload/*Channel.ts` files.** They are imported by both preload and main; importing any other preload file into the main process breaks the build.

## Knip

- **A deliberately exhaustive export is kept with a `@public` JSDoc tag, not with a knip ignore entry.** Knip's `isAlwaysIgnored` (`node_modules/knip/dist/util/tag.js`) drops anything tagged `@public`, `@beta` or `@alias`, and the tag on an `enum` covers all of its members — one line on `DataType` silenced the 27 "unused exported enum members". Prefer it to `ignore`/`ignoreDependencies` in `knip.json`: it sits next to the thing it protects, survives a rename, and does not blanket the rest of the file. Same treatment for a type kept for a future use (`ForeignKeyRow`, `src/sql/types.ts`, kept on the user's request 2026-09-02): re-export it and tag it, rather than un-exporting it — an unexported unused type is an eslint `no-unused-vars` error, so knip's "remove the export" advice just moves the failure.
- **Before dismissing an "unused dependency" as a knip bug, read the dependents' `package.json`.** `@nivo/core` looked required "for the rest of nivo", but `@nivo/bar` and `@nivo/line` list it in their own `dependencies` (pinned exactly, `0.99.0`), never as a `peerDependency` — checked back to 0.84.0. Nothing in `src/` imports it, so declaring it is redundant and knip was right. Verified by removing it: install, `yarn lint`, 753 tests and a renderer `vite build` all pass, and `node_modules/@nivo/core` is still there. The general check: `npm view <pkg>@<version> peerDependencies dependencies.<candidate>` distinguishes "the ecosystem asks me to declare this" from "an install-doc habit".
- **The `.mdx` configuration hint has nothing to do with having `.mdx` files.** Knip's Storybook plugin registers an `.mdx` compiler as soon as `storybook` is a dependency (`plugins/storybook/index.js` → `compilers/mdx.js`), and `WorkspaceWorker` then emits `project-extension-excluded` for every compiler extension the `project` glob leaves out — the repo has zero `.mdx` files. Adding `mdx` to the glob clears it and makes imports inside a future Storybook docs page followable.

## UI state and persistence

- **A view toggle is session state until the user asks for it to be remembered.** Adding "View > Toggle path" (2026-09-09) I stored the value in `config.json` — a `showPath` key, a `setShowPath`, a subscription in `ConfigurationContextProvider`, two tests — and the user cut all of it: « pas besoin de persistance dans la config. On garde l'état local ». The state now lives where it is read: the `checked` of the menu item in the main process, a `useState` in the component in the renderer, and the build decides again at every start. Reading "the default stays dev / prod" as "so there is a stored value that overrides it" was my own extrapolation, not the ask. Rule: persist a preference when the user says it must survive a restart; otherwise the cheapest state is the local one, and the diff is a third of the size.
- **A timing claim gets measured, not reasoned about — and this one was wrong.** I wrote that `window.isDev`, exposed from an `ipcRenderer.invoke(...).then(...)` in the preload, could not be captured at mount, so `useState(window.isDev)` risked freezing `undefined`; the component held an override (`useState<boolean | undefined>`) and resolved `showPath ?? window.isDev` at render. The user tried the plain `useState(window.isDev)` (2026-09-09): « ça fonctionne très bien ». Measured afterwards with a 1ms sampler installed through `Page.addScriptToEvaluateOnNewDocument`: `window.isDev` is indeed `undefined` at document start *and* at the first microtask, but it is defined at **~90ms** while `Root` first renders at **~648ms** — because `ConfigurationContextProvider` renders `null` until *its* IPC answer comes back, so anything under it mounts after at least one completed round trip. The race is real in the abstract and cannot bite in this tree. Same family as the `named-placeholders` lesson: don't write a rule about async ordering from the shape of the code, sample it. And a caveat costs code — that one bought a wider state type and a `??` for nothing.

## Patching a third-party build tool

- **Search the upstream trackers before writing the workaround, and cite the issue in the code.** Fixing the Fedora install conflict (2026-09-10) I went straight to patching `electron-installer-redhat`, only saying "electron-builder applies the same fix". The user asked « c'est bizarre que ce ne soit pas une issue connue […] vérifie » — and it is one: [electron/forge#3594](https://github.com/electron/forge/issues/3594), open since 2024-05, zero comments, no PR, and `electron-installer-redhat` has nothing on the subject (a code search for `_build_id_links` returns 0 hits in both repos). The search costs two `gh search issues` calls and it changes what the patch is worth: a link that tells the next reader the workaround is not folklore, and the condition under which it can be deleted. Rule: any monkey-patch of a dependency carries the upstream issue URL and the date it was last checked.
- **A packaging claim gets built, not argued.** The proof that `%global _build_id_links none` removes the conflicting symlinks was one `docker run ubuntu:24.04` (the rpm the CI runner has, 4.18.2) over a fake staging tree holding the real Electron ELF binaries: three of the six build-ids the user's `dnf` printed came back byte-identical in the "without" build and vanished in the "with" one. Do not run it on the Fedora host — rpm ≥ 4.20 breaks `electron-installer-redhat`'s `%install` outright ([forge#3701](https://github.com/electron/forge/issues/3701)), so a local `yarn make` fails for an unrelated reason and proves nothing.
- **An upstream PR is a hypothesis until it is run.** The user linked [electron-installer-redhat#347](https://github.com/electron-userland/electron-installer-redhat/pull/347), whose author states it was tested on rpmbuild 4.18.2 and 4.20.1; built against the installer's real staging layout it fails on both 4.20.1 and 6.0.2, because since rpm 4.20 `%{_builddir}` already expands to `<_topdir>/BUILD/<name>-<version>-build` — the per-package subdirectory the installer never writes into (its `baseAppDir` is `BUILD/usr`). The same three-image matrix that disproved it found what does work everywhere: `%{_topdir}/BUILD/usr/*`, `_topdir` being the one path the installer defines itself. Cost: one docker run per rpm major.
- **A dependency is patched with `yarn patch`, not with a wrapper class.** I had worked the two spec fixes around the package — a `MakerRpm` subclass monkey-patching `Installer.prototype.createSpec` at build time, ~130 lines with its own guard and its own self-disabling logic. The user asked for « un truc de une ou deux ligne qui ressemble à un patch git »: `yarn patch electron-installer-redhat`, edit `resources/spec.ejs`, `yarn patch-commit -s <dir>` — a 4-line diff in `.yarn/patches/` and one `resolutions` entry. It patches the thing at the source (so it is also the PR to send upstream), and a version bump makes `yarn install` fail loudly instead of a wrapper silently matching nothing. Reach for the wrapper only when the fix has to be dynamic; a constant belongs in a patch file.
- **Before bumping a transitive dependency across a major, check how its consumer loads it.** `electron-installer-redhat@4.0.0` is pure ESM; `@electron-forge/maker-rpm` is CJS and does `require('electron-installer-redhat')(…)`, so on Node 22/24 the require returns the module namespace (`{ default, Installer, __esModule }`) and calling it throws — measured in three lines rather than deduced from the changelog. The bump therefore costs a second patch (`redhat.default ?? redhat`), which is worth knowing before saying yes to the upgrade, not after.
